## 0. TL;DR（先看这 6 条）

1. **Terracotta ≠ EasyTier。** Terracotta 是"房间状态机 + 联机协议（Scaffolding）+ 平台外壳"（AGPL-3.0），EasyTier 是底下真正的 P2P 组网核心（LGPL-3.0）。Terracotta 的价值 80% 在**协议和状态机**，20% 在调 EasyTier 参数。
2. **EasyTier 官方已经有 iOS 原生客户端**：`EasyTier/EasyTier-iOS`（GPL-3.0，App Store 有售但**不含中国大陆区**，同时出 TrollStore nightly IPA）。它的 `Core/Cargo.toml` 就是 `crate-type = ["staticlib"]`、CI 装 `aarch64-apple-ios` target —— **"Rust 能不能编到 iOS" 这个问题已经被官方回答了"能"**。
3. **iOS 上不需要也不可能有 `/dev/net/tun`**。做法是：用 `NEPacketTunnelProvider`（Network Extension）建隧道，再把系统给的 **utun fd 注入**给 Rust 核心（官方客户端调 `set_instance_tun_fd(generation, fd)`）——**不越狱也能跑**，但需要 `com.apple.developer.networking.networkextension = packet-tunnel-provider` entitlement（Xcode 里开 Network Extensions capability 即可，App Store 应用也是这么加）。
4. **房间码里直接编码了 EasyTier 的网络名和密钥**（`U/NNNN-NNNN-SSSS-SSSS` → `scaffolding-mc-NNNN-NNNN` / `SSSS-SSSS`，见 §1.4）。这意味着：**iOS 只要实现"读房间码 + 起 EasyTier + 按 Scaffolding 协议问房主要端口"，就能加入安卓 ZL2 开的房，完全不需要移植 Terracotta 本体**。这是本方案最关键的一处杠杆。
5. **推荐路线 A′**（不是"完整移植 EasyTier"那么重，也不是"调外部 App"那么轻）：`EasyTier 核心（Rust 静态库）+ NE 隧道 + 自实现 Scaffolding 客户端/服务端`，分三阶段落地。**路线 D（同 WiFi 手输 IP）保留为永远可用的兜底**，因为它零 entitlement、零服务端成本。
6. **最大的风险不是技术，是分发与合规**：Network Extension 类"VPN"应用在中国大陆区 App Store 上不了架（EasyTier-iOS 自己就写明"除中国大陆地区外"），当前项目本来就走"未签名 IPA + TrollStore/AltStore"的路子——那 Network Extension 能不能生效，取决于**安装方式带不带 entitlement**，这是第一个必须先在真机验证的开关（§2.5、§5 R1）。

### 1.2 分层：谁是壳，谁是核（已确认）

```
┌─────────────────────────────────────────────────────────┐
│ 外壳层（每个平台一份，互不复用）                          │
│  CLI 参数 / Tauri-GUI / Web 控制台 / HTTP API(127.0.0.1)  │
│  Android: ffi/TerracottaAndroidAPI.java + libterracotta.so│
├─────────────────────────────────────────────────────────┤
│ Terracotta 内核（Rust，跨平台复用）                       │
│  · 房间状态机（8 个状态，见 §1.5）                        │
│  · 房间码生成/解析（3 种格式，见 §1.6）                   │
│  · Scaffolding 协议（见 §1.4，TCP 私有协议）              │
│  · 本机 MC 端口扫描（host-scanning 状态）                 │
│  · EasyTier 参数拼接（network-name / secret / 公共节点）  │
│  · 本地 TCP 中继（guest-ok 后给 127.0.0.1:port 直连地址） │
├─────────────────────────────────────────────────────────┤
│ EasyTier（Rust，真正干活的 P2P 组网）                     │
│  · NAT 打洞 / 中继 / 加密 / 虚拟 IP 分配 / 路由           │
└─────────────────────────────────────────────────────────┘
```

**结论**：Terracotta 是"**联机产品**"，EasyTier 是"**组网库**"。想复刻 ZL2 的联机体验，需要的是"协议 + 状态机 + EasyTier"，三者中只有 EasyTier 我们直接复用（LGPL，宽松得多）。

### 1.3 通信模型

**角色**（已确认，`internal-protocol.md`）：

| 名词 | 含义 |
|---|---|
| 联机中心（Host） | 与 Minecraft 服务器同机运行；生成房间码；对外提供 Scaffolding TCP 服务；EasyTier hostname 固定为 `scaffolding-mc-server-{port}` |
| 联机房客（Guest） | 加入 EasyTier 网络后，靠"联机中心发现协议"找到 host 的虚拟 IP，问出 MC 端口 |

**一次完整联机的数据流**（由 §1.7 的 Android API 文档与 HTTP API 文档交叉确认）：

```
房主                                         房客
 ① 启动 MC → 存档内「对局域网开放」
 ② Terracotta 扫描本机 49152-65535，
    找到 MC 的 LAN 端口（host-scanning）
 ③ 生成房间码 U/NNNN-NNNN-SSSS-SSSS
 ④ 以 network-name=scaffolding-mc-NNNN-NNNN、
    network-secret=SSSS-SSSS 起 EasyTier，
    连若干公共节点                     ←─── 同一个 network-name/secret 起 EasyTier
 ⑤ EasyTier 打洞/中继建立 P2P 通道  ←──────→  P2P（UDP 直连，失败则公共节点中继）
 ⑥ 在虚拟网卡上开 TCP 服务（端口 p）←───────  向 host 的虚拟 IP: p 发 c:ping / c:protocols
                                                 / c:server_port 问出 MC 端口
 ⑦ 房主把 MC 端口回给房客（c:server_port）
 ⑧ （可选）向本机 LAN 广播 MC 大厅条目，    ⑨ 在 127.0.0.1 开本地 TCP 中继，
    让玩家在多人游戏列表「双击」进入            把流量转给 host 虚拟 IP:MC端口
```

要点（都已确认）：

- **P2P 优先，中继兜底**：EasyTier 自动 NAT 穿透（README 称支持 NAT4-NAT4、UDP/IPv6 打洞），失败才走共享节点中继。所以"陶瓦联机不经过第三方服务器转发"这句话**只对打洞成功的房间成立**——这是 ZL2 界面里那句免责声明的真实含义。
- **房间成员靠心跳维持**：`c:player_ping` 每 5 秒一次，10 秒无心跳即从成员列表移除（HTTP API 文档）。
- **NAT 难度提示**：`guest-starting` 状态带 `difficulty` 字段（`UNKNOWN/EASIEST/SIMPLE/MEDIUM/TOUGH`）。
- **MC 端口是随机端口**（原版「对局域网开放」的端口是随机的），所以必须有"扫描/询问"这一步，不能写死 25565。

### 1.4 房间码 = EasyTier 网络名 + 密钥（已确认，本方案最关键的一节）

`internal-protocol.md` 原文规定：

- 房间码形如 **`U/NNNN-NNNN-SSSS-SSSS`**；
- `N`/`S` 为任意大写字母（**排除 I 和 O**）和数字；
- 把字符按 `0-9、A-H、J-N、P-Z` 映射到 `[0, 33]` 后，按"小端序"读出的整数应能被 **7 整除**（这是给房间码加校验位的手法）；
- **EasyTier 网络名 = `scaffolding-mc-NNNN-NNNN`**，**网络密钥 = `SSSS-SSSS`**；
- 联机中心 hostname = `scaffolding-mc-server-{port}`（port ∈ (1024, 65535]）；
- 例：房间码 `U/YNZE-U61D-2206-HXRG` → 网络名 `scaffolding-mc-YNZE-U61D`、密钥 `2206-HXRG`。

**这意味着什么**：

> 拿到 n 位房间码的任何一个客户端，**不需要连 Terracotta 的服务器、不需要任何鉴权**，就能推出 EasyTier 的 network-name / network-secret，直接组网。Terracotta 本体在这个环节只做"生成码 + 拼 EasyTier 参数 + 跑状态机"。

**因此有两个直接可用的工程推论（推断，但依据很强）**：

- **A. iOS 可以只做房客**：`解析房间码 → 用推出来的 name/secret + 公共节点列表起 EasyTier → 等 host hostname 出现 → 对它发 Scaffolding 请求拿 MC 端口 → 在 127.0.0.1 起本地中继（或直接连 host 虚拟 IP）`。这样 iOS 能加入**安卓 ZL2 / HMCL / PCL** 开的房，互通性极好，而**完全不需要 Terracotta 的代码**（不涉及 AGPL）。
- **B. iOS 也可以做房主**：自己生成房间码（含 mod-7 校验）、跑 EasyTier、在虚拟网卡上开一个 Scaffolding TCP 服务实现 5 条基础命令（`c:ping` `c:protocols` `c:server_port` `c:player_ping` `c:player_profiles_list`），并扫本机 MC 端口。**这部分是纯 Swift 业务代码，几百行量级**，不碰 GPL/AGPL。

### 1.5 房间状态机（已确认，HTTP API 文档）

| state | 含义 | 关键字段 |
|---|---|---|
| `waiting` | 待机 | `index` |
| `host-scanning` | 房主：正在扫描本机 MC 端口 | — |
| `host-starting` | 房主：正在建房 | `room` |
| `host-ok` | 房主：房间就绪 | `room`、`profile_index`、`profiles[]` |
| `guest-connecting` | 房客：正在连 | `room` |
| `guest-starting` | 房客：EasyTier 起网中 | `room`、`difficulty` |
| `guest-ok` | 房客：加入成功 | `url`（`127.0.0.1` 或 `127.0.0.1:{端口}`）、`profiles[]` |
| `exception` | 异常 | `type`(0-5) |

- `index` **单调递增**，每次状态/成员变化都自增；轮询方应忽略 `index` 未增大的响应（约 500ms 轮询）。
- `exception.type`：`0` 连不上房主 / `1` 与房主连接中断 / `2` 房客 EasyTier 崩 / `3` 房主 EasyTier 崩 / `4` 房主 MC 失联（房间自动关闭）/ `5` 脚手架协议错误。要回待机需调 `/state/ide`。
- `profiles[].kind`：`HOST` / `LOCAL` / `GUEST`；`machine_id` 为设备唯一标识。

> 这套状态机对 iOS 客户端是**最好的参考实现**：UI 上"创建/加入房间"的每个中间态（扫描中、连接中、难度评估、异常分型）都能一一对应，可以直接照抄状态名，避免自己臆造交互。

### 1.6 三种房间码（已确认）

Android API 的 `parseRoomCode()` 返回枚举：

```java
public enum RoomType { TERRACOTTA_LEGACY, PCL2CE, SCAFFOLDING }
```

- `SCAFFOLDING` = 本文 §1.4 的 `U/NNNN-...` 格式，**公开文档化的那一种**；
- `TERRACOTTA_LEGACY`、`PCL2CE` = 另两种历史/分支格式，**具体格式：未查证**（`http-api.md` 里有「房间邀请码格式」标题但正文为空）。

工程建议：iOS 第一版**只认 `U/` 开头 + mod-7 校验**的 Scaffolding 房码，其余格式明确报"暂不支持此房码"，不要猜格式。

### 1.7 安卓版是怎么集成的（已确认，这是 iOS 的最好参照）

**Terracotta 侧**：`ffi/` 目录下只有一个文件 `TerracottaAndroidAPI.java`（"支持安卓 #88"，2025-12-13）。它是一层 **JNI 薄封装**，Rust 侧编译成 `libterracotta.so`。关键 API：

```java
static Metadata initialize(Context context, VpnServiceCallback callback); // 进程级单例
static String  getState();                       // JSON，同 HTTP API 的 /state
static void    setWaiting();                     // 回待机
static void    setScanning(String room, String player);      // 开房（room=null 则新建）
static boolean setGuesting(String room, String player);      // 加入
static RoomType parseRoomCode(String room);      // 秒级，UI 可用
static Reader  collectLogs();
static native ... // start0 / getState0 / setScanning0 / setGuesting0 / verifyRoomCode0 ...
```

**"请求—响应"式拿 TUN**（这套协议在 iOS 上会原样重演，只是换成 NE）：

```java
// 原生层在 Rust 工作线程回调：
public interface VpnServiceCallback { void onStartVpnService(); }

// Java 层拿到一次性请求对象，30 秒内必须 startVpnService 或 reject：
VpnServiceRequest req = TerracottaAndroidAPI.getPendingVpnServiceRequest();
ParcelFileDescriptor tun = req.startVpnService(builder); // 内部 builder.establish()
// fd 以「共享(getFd)非 detach」方式交给原生层，ParcelFileDescriptor 由 App 持有
```

预置的 builder 内容：EasyTier 分配的虚拟 IP（`addAddress`）、DNS `223.5.5.5`/`114.114.114.114`、若干 `addRoute` —— **且文档明确警告"不要改动已配置的地址与路由，否则 EasyTier 无法工作"**。

**ZL2 侧**（`ZalithLauncher/ZalithLauncher2` 的 `Terracotta/` 模块，已确认）：

```
Terracotta/
  build.gradle.kts        namespace = "net.burningtnt.terracotta"
                          dependencies { implementation(libs.androidx.appcompat) }   // 仅 appcompat
  src/main/java/net/burningtnt/terracotta/...
  src/main/jniLibs/       ← libterracotta.so（各 ABI）
  src/main/res/raw/       ← 教程文案
  src/main/AndroidManifest.xml
```

即：**ZL2 没有 fork Terracotta，而是把「Java 接入类 + 预编译 .so」直接搬进自己的 Gradle 模块**，外层再写一个 `VpnService` 子类承接请求。FCL（FoldCraftLauncher）用的是同一套（其模块命名空间同样是 `net.burningtnt.terracotta`，职责标注为 "VPN service"）。

**对 iOS 的三条直接启示**：

1. **"内核 Rust + 平台薄壳"这条路 Terracotta 自己已经验证过一遍**（Android JNI ↔ iOS FFI 是同构的）。
2. iOS 上**没有"进程级单例 + VpnService 回调"这种便利**：VPN 必须在**独立进程的 Network Extension** 里跑，主 App 只能通过 `NETunnelProviderManager` + App Group + `sendProviderMessage` 通信。这是移植的主要复杂度来源（§2.4）。
3. ZL2 的 UI 文案（用户须知/房主教程/房客教程）与状态名可以直接沿用，我们已有的 `MultiplayerScreen`/`MultiplayerRoomScreen` 骨架正好对着这套状态机。

### 1.8 许可证传染性（已确认，务必在动手前定调）

| 组件 | 许可证 | 若我们静态链接它 |
|---|---|---|
| EasyTier | **LGPL-3.0** | 可用，但需满足 LGPL：提供可重链接手段（目标文件/源码）。我们 App 已是 GPL-3.0（Amethyst），天然满足"给源码" |
| EasyTier-iOS（官方客户端代码） | **GPL-3.0** | 与 GPL-3.0 的 App **兼容**，可直接借代码（保留版权声明） |
| Terracotta | **AGPL-3.0-or-later** + 例外 | 静态链入 → **整个 App 变 AGPL**（网络服务也要提供源码）；只有"独立进程 + HTTP API"才不受影响 |
| ZL2 本体 | GPL-3.0 + 附加条款 | 附加条款禁止沿用 "ZalithLauncher"/"ZL" 名称（`STATUS.md` 已记录） |

**结论**：路线 A′ 复用 **EasyTier + EasyTier-iOS（LGPL/GPL）**，不碰 Terracotta 源码 → 许可证面**不扩大**，这是选 A′ 而不选"移植 Terracotta"的第二个理由（第一个是工作量）。

## 2. EasyTier 能不能编到 iOS

### 2.1 构建方式（已确认）

`EasyTier/EasyTier` 是 Cargo workspace，目录包括：

```
easytier/          ← 库 crate（crate-type = lib；bin: easytier-core / easytier-cli）
easytier-core/     ← 核心实现（tun / route / peer 管理）
easytier-proto/    ← protobuf（prost，构建需要 protoc）
easytier-gui/      ← Tauri GUI
easytier-js/       ← WASI/WASM
easytier-web/      ← Web 控制台
tauri-plugin-vpnservice/
android.nix        ← Android 构建用 nix 表达式
```

`easytier/Cargo.toml` 关键事实：

- 版本 `2.7.0`；`license-file = "LICENSE"`（LGPL-3.0）；
- 默认 features 很重：`cli, wireguard, websocket, smoltcp, tun, socks5, kcp, quic, faketcp, magic-dns, zstd, upnp, icmp-proxy, management, endpoint-discovery, extended-services, linux-netlink, tcp-hole-punch`；
- 有独立 feature **`macos-ne = []`**，注释原文 `# For Network Extension on macOS`（**这就是 Apple NE 的官方开关**）；
- TUN 依赖：`tun = { package = "tun-easytier", git = "https://github.com/EasyTier/rust-tun", ... }`（可选）；
- 平台条件依赖里 `machine-uid` 只对 `linux/macos/windows/freebsd` 生效 —— **iOS 不在其中，编译期不会去读 SMBios/注册表**，这是个好信号（推断：iOS 上"机器唯一 ID"要自己给，Terracotta 的 `machine_id` 也是同理自己生成）。

### 2.2 iOS 交叉编译：官方已经做成了（已确认）

**`EasyTier/EasyTier-iOS`**（GPL-3.0）的核心就是一个 Rust 静态库：

`Core/Cargo.toml`（原文）：

```toml
[package]
name = "easytier-ios"

[lib]
crate-type = ["staticlib"]          # ← 产出 .a，由 Xcode 链接

[profile.release]
strip = "none"

[dependencies]
easytier = { git = "https://github.com/EasyTier/EasyTier.git", tag = "v2.6.4", version = "=2.6.4", features = ["macos-ne"] }
tokio = { version = "1", features = ["rt-multi-thread", "sync", "time"] }
```

### 2.3 官方 iOS 侧的 FFI 形状（已确认，可直接照抄）

`Core/src/lib.rs` 导出的 C ABI（`#[no_mangle] pub extern "C"`）：

```c
int  init_logger(const char *path, const char *level, const char *subsystem, const char **err);
int  clear_logger(const char **err);
void free_string(const char *value);
int  run_network_instance(const char *cfg_str, void (*callback)(const char *json), const char **err);
int  stop_network_instance(void);
int  set_instance_tun_fd(uint64_t generation, int fd, const char **err);   // ★ 关键
int  complete_instance_setup(uint64_t generation, bool success, const char *error);
int  get_instance_status(const char **json, const char **err);
int  get_running_info(const char **json, const char **err);
int  start_config_server_client(...);   // Web 模式，iOS 用不到
```

以及 Swift 侧的桥接头 `EasyTierNetworkExtension-Bridging-Header.h`、`easytier_ios.h`。

**几个从源码里读出来的"坑"，做方案时必须知道**（已确认，`Core/src/instance.rs`）：

1. **一个 NE 进程只支持一个网络实例**，源码里有硬错误串：`"Apple client supports one network instance"`。→ 我们的产品形态（一次一个房间）刚好匹配，但不要设计"同时进多个网络"。
2. **上游 EasyTier 2.6.4 没有"API ready"回调**，官方客户端只能**每 250ms 轮询** `get_instance_service()` 判断初始化完成；生命周期另有 5s 复检。→ 状态同步不能只靠事件，必须"事件 + 轮询"双保险。
3. **`generation` 代际号是防串台的核心**：`set_instance_tun_fd` / `complete_instance_setup` 都带 `generation`，重启会话后旧回调一律作废。→ 我们的 Swift 层必须原样保留这个模式，否则"退出房间再进另一个房间"会拿到上一次的 fd。
4. **超时值**：启动 10s、设置应用 20s（源码常量 `START_TIMEOUT` / `SETUP_TIMEOUT`）。→ 弱网下要给用户明确的"正在连接/超时重试"文案，而不是无限转圈。

### 2.4 iOS 上 TUN 怎么办：NEPacketTunnelProvider（已确认）

**事实**：iOS 沙盒里**不能**打开 `/dev/net/tun`，也不能自己 `socket(AF_SYSTEM, ...)` 建 utun。唯一合法路径是 Network Extension 的 `packet-tunnel-provider`。

`EasyTierNetworkExtension/EasyTierNetworkExtension.entitlements`（原文）：

```xml
<key>com.apple.developer.networking.networkextension</key>
<array><string>packet-tunnel-provider</string></array>
<key>com.apple.security.application-groups</key>
<array><string>group.cn.easytier</string></array>
```

Apple 官方对该 entitlement 的说明（已确认，developer.apple.com）：

> **packet-tunnel-provider** — The APIs you use to tunnel IP packets to a remote network using any custom tunneling protocol.
> To add this entitlement to an App Store app, **enable the Network Extensions capability in Xcode**.

即：**不需要向 Apple 单独申请**（对比 `com.apple.developer.networking.vpn.api`「Personal VPN」那种要报批的），付费开发者账号在 Xcode 里勾 capability 即可；但**必须有付费账号/能带 entitlement 的签名**，免费个人账号是否可行 —— **未查证**。

**官方客户端怎么把 utun fd 交给 Rust**（已确认，`PacketTunnelProvider.swift` + `TunnelHelper.swift`）：

```swift
// 主路径：KVC 拿 NEPacketTunnelFlow 内部 socket 的 fd
guard let tunFd = self.packetFlow.value(forKeyPath: "socket.fileDescriptor") as? Int32
        ?? tunnelFileDescriptor() else { ... }        // 备用路径见下
_ = setNonBlocking(fd: tunFd)
let ret = set_instance_tun_fd(instanceGeneration, tunFd, &errPtr)   // → Rust 侧
```

```swift
// 备用路径：遍历 0...1024 的 fd，用 getpeername 找 AF_SYSTEM + com.apple.net.utun_control
func tunnelFileDescriptor() -> Int32? { ... CTLIOCGINFO / ctl_info ... }
```

配套的 `NEPacketTunnelNetworkSettings` 由 Rust 侧回传的 `TunnelOptions`（`ipv4/ipv6/mtu/routes/magicDNS/dns`）填：

```swift
let settings = NEPacketTunnelNetworkSettings(tunnelRemoteAddress: "127.0.0.1")
settings.ipv4Settings = ... // addresses + includedRoutes（EasyTier 虚拟网段）
settings.mtu = ...
setTunnelNetworkSettings(settings) { error in ... }   // 完成后再注入 tun fd
```

> **风险提示（务必写进风险台账）**：`value(forKeyPath: "socket.fileDescriptor")` 是**用 KVC 摸私有内部键**。EasyTier-iOS 已在 App Store 上架（说明审核未拦），但这是**审核/系统版本双重风险点**；备用路径（扫 fd + `getpeername`）不涉私有 API 但**性能差且未来可能失效**。若走 App Store，需准备好被拒的应对（申诉/改用私有 API 替代方案 —— 目前**没有公开的官方替代**，这是 iOS 跑一切用户态 VPN 的公共难题）。

### 2.5 iOS 沙盒结论（逐条回答任务里的问题）

| 问题 | 结论 |
|---|---|
| 能不能创建 TUN 设备？ | **不能自己 `open("/dev/net/tun")`**；能通过 `NEPacketTunnelProvider` 由系统**代建 utun 并把 fd 给你**。 |
| NEPacketTunnelProvider 需要什么 entitlement？ | `com.apple.developer.networking.networkextension` = `["packet-tunnel-provider"]`（Xcode 勾 Network Extensions capability），外加上层 App 与 Extension 共享的 **App Group**。 |
| **不越狱能跑吗？** | **能**——前提是安装包带上述 entitlement 与匹配的 provisioning profile。官方客户端即"App Store 版 + TrollStore ad-hoc 版（pre-built IPA，自带 NE/AppGroup entitlements 签名）"双轨发行，**证明两条路都成立**。 |
| 模拟器能测吗？ | **未查证**（Network Extension 在模拟器上的支持历来不完整）。工程上按"必须真机"排期。 |
| 需要什么账号？ | 走正规签名 → **付费 Apple Developer Program**（$99/年）；走 TrollStore → **免账号**，但受 iOS 版本限制（TrollStore 支持的版本区间未查证）。 |
| 后台能一直跑吗？ | Extension 独立进程，主 App 挂起后隧道通常继续；但 Extension **有内存上限**（具体数值 **未查证**，社区经验在几十 MB 量级）。**App 内还跑着 JVM**，两个进程同时吃内存 → 低端机有 jetsam 风险。 |

### 2.6 依赖与体积（部分未查证）

- 必装构建依赖：`protoc`（`easytier-proto` 的 prost 构建脚本要它）、Rust toolchain、Xcode。
- Rust 依赖里值得一提的：`tokio`（多线程 runtime）、`rustls`/`ring`、`quinn`(QUIC)、`boringtun`(WireGuard)、`smoltcp`、`tun-easytier`、`hickory-*`(DNS)、`sys-locale`、`rust-i18n`。**都能在 iOS 上编**（官方客户端已证），但 `ring`/`boringtun` 会增加体积与编译时间。
- **静态库/最终 App 体积：未查证**（本轮没编）。参照：我们现在的 IPA 是 **50.92 MB（解压 158.2 MB）**（`STATUS.md`），EasyTier 静态库预计会再加一块，需实测后决定是否裁剪 features（如关掉 `wireguard/cli/quic/kcp/upnp/magic-dns`，见 §4 的裁剪清单）。
- **编译时间**：首次 cargo build（含 protoc 代码生成、`ring`、`quinn`）在 macOS runner 上**估计 10-25 分钟**（推断，未实测）；建议 CI 加 `Swatinem/rust-cache` 并只编 `aarch64-apple-ios`。

|---|---|---|---|
| **D. 同 WiFi 手输 IP**（任务里的 D） | 不做 P2P；MC 对局域网开放后，房客在多人游戏里填 `192.168.x.x:端口` | ✅ 只需 `NSLocalNetworkUsageDescription`（**iOS 14+ 访问局域网地址会弹权限**，见 Apple Local Network Privacy FAQ：*Making an outgoing TCP connection — yes 需要授权*） | 只能同网段；跨网/蜂窝完全不可用；但**永远能当作兜底** |

## 3. 四种路线对比

先说清"工作量"的度量：以**一个熟练 iOS + Rust 工程师**、已有本工程（SwiftUI + Amethyst 核心 + macOS CI）为基准，估**净新增工作量**（不含联调排障的不可控时间）。

| # | 路线 | 核心做法 | 工作量（人日） | 可行性 | 用户体验 | 主要风险 |
|---|---|---|---|---|---|---|
| **A** | 完整移植 EasyTier（Rust→iOS 静态库） | 编 `libeasytier.a`；新增 NE target；FFI 桥；自实现房间/协议；自建公共节点 | **25–40** | ✅ **高**（官方已做成，等于抄作业） | ★★★★★ 真·邀请码、跨网、安卓/iOS 互通 | 分发（大陆上架/签名）、NE 私有 API 审核、内存、公共节点运维 |

### 3.1 逐条说人话

**A / A′ —— 为什么"其实没那么难"**

因为 `EasyTier-iOS` 把最难的三件事全做完了并且开源（GPL-3.0，与我们的 App 许可同族）：
1. Rust → iOS 静态库的构建脚本（3 行 shell）；
2. `NEPacketTunnelProvider` ↔ Rust 的 fd 注入 + 状态机 + 代际号防串台（`PacketTunnelProvider.swift` 约 500 行）；
3. `entitlements` / App Group / 日志（`tracing-oslog`）/ 前后台生命周期。

我们要写的其实是**业务层**：房间码生成与校验（mod-7）、Scaffolding 五条命令、本机 MC 端口扫描、UI 状态机、以及"给 MC 客户端用的本地中继/服务器列表注入"。

**B —— 为什么看起来最省事其实最坑**

iOS 不允许一个 App 去"驱动"另一个 App 完成建网并回传结果：URL Scheme 只能"唤起"，拿不到 Tailscale 的虚拟 IP，也拿不到"已连接"状态；用户必须在两个 App 之间手工抄 IP。ZL2 的卖点恰恰是"输入 6 位码就行"，B 直接把这个卖点丢了。

**C —— 概念错位**

`app-proxy-provider` 是"按连接代理"，EasyTier 需要的是"一块虚拟网卡 + 路由表 + 任意 IP 的 IP 包"。用 C 去模拟 A，等于自己重写 EasyTier 的数据面，**成本高于 A**。

**D —— 必须有，但不能只有**

D 是唯一"零 entitlement、零服务端、今天就能做"的方案，且它天然覆盖"同屋/同宿舍"这个高频场景。**建议 D 作为产品的"局域网联机"入口长期保留**，同时它也是 A′ 出问题时的降级路径。

## 4. 推荐路线 + 分步实施计划

### 4.1 推荐：A′（EasyTier + NE + 自实现 Scaffolding），D 作兜底

**为什么不是 A**：Terracotta 本体的价值（房间状态机 + 协议）我们已经从**公开文档**里拿到了规格（§1.4–1.6），自己实现可控且**不引入 AGPL**；移植 Terracotta 需要写一套 iOS FFI 替代 `TerracottaAndroidAPI.java`（它深度耦合 `VpnService`/`ParcelFileDescriptor`/`Context`），改造成本高于重写。

**为什么不是 D 或 B**：产品目标是"像 ZL2 那样输入邀请码就联机"，D 给不了跨网，B 给不了体验。

**为什么现在就能定**：技术路径上唯一的"未知"（Rust 能不能在 iOS 上跑 + 能不能拿到 tun）**已经被官方客户端在 App Store 上验证**。剩下的是**分发与审核**风险，属于可决策项（§5 R1），不是调研空白。

### 4.2 里程碑（每个都有明确验收，避免"做完才发现不通"）

#### M0. 可行性验证（1–2 人日，**先做这个，别的都别做**）

目标：证明"我们的签名方式下，NE 能起来并把 fd 交给 Rust"。

- [ ] CI 加一步：`rustup target add aarch64-apple-ios` + 编 `EasyTier-iOS/Core`（或我们自己 clone 的 `Core/`）→ 得到 `libeasytier_ios.a`；
- [ ] 新增 NE target + entitlements（见 §4.3 代码骨架）；
- [ ] 写一个**最小** `PacketTunnelProvider`：启动 → 打印 `set_instance_tun_fd` 返回值 → 立刻 stop；
- [ ] 用 `xcrun devicectl` / Xcode 真机跑一次，看到日志即算过。

**验收**：真机日志出现 `set_instance_tun_fd ... ret=0`。若失败在签名（`NEProviderStartErrorDomain`），直接转 §5 R1 的决策，**不要继续后面的工作**。

#### M1. 房客模式（6–8 人日，**这是第一个能演示的功能**）

目标：**iOS 加入安卓 ZL2 开的房**（不需要自己做房主，互通性一口气验证）。

- [ ] `RoomCode.swift`：解析 `U/NNNN-NNNN-SSSS-SSSS` → 校验字符集/长度/mod-7 → 产出 `(networkName, networkSecret)`；
- [ ] `EasyTierCore.swift`：C 接口封装（`run_network_instance` / `set_instance_tun_fd` / `get_instance_status` / `stop_network_instance`），带 `generation` 防串台；
- [ ] TOML 配置生成：`network_name` / `network_secret` / `ipv4`（房客留空由 EasyTier 分配）/ `listeners` / 公共节点 peer（先写死 §1.1 里那两个社区节点，**上线前必须换/自建**）；
- [ ] 服务发现：轮询 `get_running_info`，在 peer/hostname 里找 `scaffolding-mc-server-{port}`，拿 host 虚拟 IP；
- [ ] Scaffolding 客户端：TCP 连 `hostIP:port`，实现 `c:ping` → `c:protocols` → `c:server_port`（大端 u16）；拿到 MC 端口；
- [ ] 本地中继：在 `127.0.0.1:<空闲端口>` 监听，转发到 `hostIP:mcPort`（这样 MC 客户端只需连 localhost，绕开"大厅广播"）；
- [ ] UI：把 `MultiplayerRoomScreen` 的假邀请码换成真状态机（`waiting/guest-connecting/guest-starting/guest-ok/exception`），异常分型照抄 §1.5。

**验收**：安卓 ZL2 开房 → iOS 输邀请码 → **能进世界**（同一 WiFi 与跨网各测一次）。这一条跑通，整个方案的商业价值就已经成立。

#### M2. 房主模式（8–12 人日）

- [ ] 房间码生成（含 mod-7 校验，保证能被 HMCL/PCL/ZL2 识别）；
- [ ] 本机 MC 端口扫描：扫 `49152-65535` 的 loopback TCP（Terracotta 的 `host-scanning` 就是这么干的；比解析 JVM 日志可靠）；
- [ ] 在虚拟网卡上起 Scaffolding **服务端**：`c:ping`、`c:protocols`、`c:server_port`、`c:player_ping`（5s 心跳/10s 超时）、`c:player_profiles_list`；
- [ ] hostname 设为 `scaffolding-mc-server-{port}`（让别人的客户端能发现我们）;

### 4.3 落地时要改的地方（**本轮不实施，仅说明范围**）

1. `project.yml`：新增两个 target（App Extension + 共享 framework）与 entitlements 引用（示意，**勿直接抄字段名以外的假设**）：

```yaml
targets:
  ZL2iOS:
    entitlements: { path: src/ZL2iOS.entitlements }
    dependencies:
      - target: ZL2Tunnel
      - target: EasyTierShared
  ZL2Tunnel:                       # type: app-extension, NEPacketTunnelProvider
    type: app-extension
    platform: iOS
    sources: [src/Tunnel]
    entitlements: { path: src/ZL2Tunnel.entitlements }   # packet-tunnel-provider + app group
  EasyTierShared:                  # 主 App 与 Extension 共享的模型/日志/App Group
    type: framework
    sources: [src/Shared]
```

2. `build.yml`：在 "Build Amethyst core" 之后插入 Rust 构建步：

```yaml
      - name: Build EasyTier core (Rust 静态库)
        run: |
          rustup target add aarch64-apple-ios
          brew install protobuf   # 提供 protoc
          git clone --depth 1 --branch v2.6.4 https://github.com/EasyTier/EasyTier.git /tmp/easytier
          # 复用官方 Core 的 Cargo 工程（或我们自建一个同构 crate）
          cargo build --release --target aarch64-apple-ios --manifest-path core-easytier/Cargo.toml
          ls -lh core-easytier/target/aarch64-apple-ios/release/*.a
```

3. 链接：`OTHER_LDFLAGS[sdk=iphoneos*]` 追加 `-leasytier_ios`、`-lc++`（Rust 静态库的 C++ 依赖视 features 而定，**未查证**是否需要）+ `LIBRARY_SEARCH_PATHS` 指向产物目录。
4. Swift 侧新增文件（**建议放 `src/Multiplayer/`，与现有 `MiscScreens` 解耦**）：`RoomCode.swift`、`EasyTierCore.swift`、`ScaffoldingClient.swift`、`ScaffoldingServer.swift`、`LocalRelay.swift`、`TunnelManager.swift`（主 App ↔ NE 的 `NETunnelProviderManager` 封装）、`ServersDatWriter.swift`。
5. 现有 `MultiplayerRoomScreen` 的假邀请码逻辑替换为真实状态机（**这是唯一要动的既有 UI 文件**）。

### 4.4 Features 裁剪建议（控体积/编译时间，待实测）

`easytier/Cargo.toml` 的默认 features 很重。iOS 首版建议 `default-features = false` + 显式开：

```
macos-ne            # 必须
smoltcp             # 用户态协议栈（NE 场景必需其一）
tracing / logging   # 诊断
```

**可先关**：`cli`（我们是库不是命令行）、`wireguard`、`quic`、`kcp`、`upnp`、`magic-dns`、`faketcp`、`socks5`、`extended-services`、`management`。
**注意**：关 `tun` 是否会导致"无 tun fd 注入路径不可用"—— 官方的 `set_tun_fd` 走的是 `NetworkInstanceManager`，与 `tun` feature 的耦合关系 **未查证**，裁剪时每关一个都要跑一次 §M0 的验证。**保守做法：第一版全默认 features，先跑通再裁。**

## 5. 风险台账（按"会不会让项目停摆"排序）

| # | 风险 | 等级 | 说明与对策 |
|---|---|---|---|
| **R1** | **签名/分发决定 NE 能不能用** | 🔴 致命 | 无 entitlement = NE 起不来，整个 A′ 直接归零。**M0 必须真机验证**。对策：付费账号 + 带 NE entitlement 的 profile（推荐）；TrollStore 路径需 ad-hoc 签 entitlements（官方 nightly 已验证可行，但依赖 iOS 版本，**未查证具体区间**）。**若 M0 不通，退回 D，不要硬扛。** |
| **R2** | 大陆区上架不可能 | 🔴 高 | EasyTier-iOS README 自己写明"App Store（除中国大陆地区外）"；VPN 类应用在大陆区实际不可上架。对策：非大陆区账号 / TestFlight / 自签 + 官网分发；产品文案不要承诺"App Store 下载"。 |
| **R3** | 私有 API（KVC 取 socket fd）审核/系统风险 | 🟠 中高 | 官方客户端已过审，但非官方保证；新 iOS 版本可能改内部键名。对策：保留 `tunnelFileDescriptor()` 兜底；监控崩溃；准备申诉材料。 |
| **R4** | MC"大厅广播"在 iOS 上需要 multicast entitlement | 🟠 中 | 向局域网发/收 **multicast 需要 `com.apple.developer.networking.multicast`，该 entitlement 要向 Apple 申请**（与 NE 不同，不是自助勾选；Apple 文档已列出该键）。对策：**不做广播**，改用"服务器列表注入（servers.dat）+ 本地中继"，绕开该权限（§M3）。 |
| **R5** | NE 进程内存上限 + App 内 JVM 共存 | 🟠 中 | 存在 jetsam 风险（具体上限**未查证**）。对策：Extension 内 tokio 改**单线程 runtime**（官方用 `new_multi_thread`，可改）；裁剪 features；低内存机型降级为提示用户关闭后台 App。 |
| **R6** | 公共节点依赖第三方 | 🟠 中 | 默认节点是社区提供的（`etnode.zkitefly.eu.org`）。对策：**上线前自建**；连多个节点提可用性；UI 里如实说明"P2P 失败时会经中继"。 |
| **R7** | 与安卓端协议版本漂移 | 🟡 中低 | Scaffolding 协议标注"仍在开发"，房间码有 3 种类型。对策：只实现 `U/` + mod-7 校验；对未知房码明确报错；跟 `v2.6.4` 钉版本。 |
| **R8** | 许可证 | 🟡 中低 | 复用 EasyTier(LGPL-3.0) + EasyTier-iOS(GPL-3.0) 与现有 GPL-3.0 App 兼容；**绝不要静态链 Terracotta（AGPL）**。对策：代码来源逐个登记（借鉴 EasyTier-iOS 的文件保留其版权头）。 |
| **R9** | 真机测试资源 | 🟡 中低 | NE 只能真机、且要两台不同网络环境。对策：至少准备 1 台 iPhone + 1 台安卓（跑 ZL2）+ 1 个手机热点做跨网测试。 |
| **R10** | 编译时间/CI 配额 | 🟢 低 | Rust 首次编译可能 10-25 分钟（推断），macOS runner 计费 ×10。对策：`Swatinem/rust-cache`、只编 device target、只在需要时触发。 |
